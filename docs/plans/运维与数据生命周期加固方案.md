# 运维与数据生命周期加固方案

> 依据：ISSUE #14 评估报告（289 Java 文件 / 25 Vue 组件 / 21 张表全量回查）。
> 原则：只动有实据的问题，每个改动点配套单测/验收，不引入不必要依赖。

## 一、问题清单与影响

| 优先级 | 问题 | 影响 | 证据 |
|---|---|---|---|
| P0-1 | 分区表建了但无分区维护、无保留策略 | 数据全落 `p_max`，分区退化为普通表，`jvm_metric` 无限增长 | `sql/init.sql` 有 `create_daily_partition` 存储过程，全仓库零调用；`@Scheduled` 仅 `JvmAlertService`/`StressScheduler` |
| P0-2 | `trace_chain` 逐条 INSERT | 单批 500 条 → 500 次往返 + 自增锁竞争，写吞吐瓶颈 | `AgentReportService#saveTraces` 循环内 `traceChainMapper.insert`；同文件 jvm/slowSql/slowCommand 均已批量 |
| P0-3 | `ProjectRegistry` 缓存无失效 + `ai_knowledge` 未纳入清理 | 新建项目 30s 内上报被整批丢弃；清理后 AI 仍检索到陈旧结论 | `exists()` 只有 `put` 无 `evict`；`DataCleanupService` 10 张表不含 `ai_knowledge`/`chat_message`（后者需先补 `app_name` 列） |
| P1-1 | 无 Actuator / 健康检查 / 启动自检 | 多机部署运维只能翻日志 | 无 `spring-boot-starter-actuator`，无 `/api/health` |
| P1-2 | 列表查询只有 `LIMIT` 无分页 | 历史数据一多既翻不了页也看不到总数 | `TraceChainMapper#query`、`SlowSqlMapper` 等 `LIMIT #{limit}`，硬顶 500/5000 |
| P1-3 | `AnalyzeCodeIssuesTool` 硬编码 `repoId=1L` | AI 一句话即误建 Issue 到仓库 1 | `lng(args, "repoId", 1L)` |
| P2-1 | 无删除项目接口 | 误导入大仓库无法回收 | `SourceController` 无 `DELETE /repos/{id}` |
| P2-2 | 无 apply-fix 回写 | 闭环断在"生成修复提示词" | 无 `/issues/{id}/apply-fix` 路由与实现 |
| P2-3 | 无压测模板沉淀 | 常用场景参数每次重填 | 无模板表/接口 |
| P3 | i18n / 无障碍 / 明暗主题 | 扩展性，按需 | 中文硬编码，全站深色硬编码 |

## 二、分批修改方案

### 批次 1（P0）：数据可靠性与写吞吐

#### P0-1 分区自动维护 + 保留策略

新增 `PartitionMaintainer`（`@Scheduled`，建议 1h 一次 + 启动时执行一次）：

1. 读取 `perf.retention` 配置：`jvm-metric-days` / `stress-sample-days` / `trace-chain-days` / `slow-sql-days`，`0` 表示不清理。
2. 对 `jvm_metric`（`collect_time`）、`stress_sample`（`sample_time`）：查询 `information_schema.PARTITIONS` 现有分区，为 T+1 / T+2 补齐 `pYYYYMMDD` 分区，并在 `p_max` 存在时用 `REORGANIZE` 保证 MAXVALUE 仍在最后。
3. 按保留期 DROP 早于阈值的分区（分区名日期解析，避免按行 DELETE 造成大事务）。
4. `trace_chain` / `slow_sql` 保留期用分批 DELETE（如每批 5000 条 + 循环），并走 `LIMIT` 保护。
5. 全部 SQL 加超时与 try/catch，失败只告警不影响主流程；执行结果落日志（新建/删除分区名与行数）。

配套：
- `application.yml` 增 `perf.retention.*`。
- 建表脚本补充分区说明与初始分区；保留期写进 `docs/design/database-design.md`。
- 单测：分区名计算（含跨月/跨年）、保留期边界（恰好在阈值当天不删）。

#### P0-2 trace 批量写

- `TraceChainMapper.xml` 增 `batchInsert`（`<foreach>` + `ON DUPLICATE KEY UPDATE`，语义与现 `insert` 一致）。
- `saveTraces` 改为先收集 list 再 `insertInChunks(batch, traceChainMapper::batchInsert)`，复用现有 `INSERT_CHUNK=200` 防 `max_allowed_packet`（`trace_json` 为重列，建议 trace 专属 chunk 更小，如 100，可配置）。
- 收敛：`saveJvmMetrics` 也改为走 `insertInChunks`（当前一次性 batch 未分片），保持四个类型统一。
- 单测：批量 SQL 拼接条数、空列表不执行、分片边界（200/201/500）。

#### P0-3 缓存失效与清理一致性

- `ProjectRegistry` 增 `evict(String projectName)` 与 `evictAll()`；`SourceManager` 在导入成功、改名、删除后调用（P2-1 删除接口一并接入）。
- `DataCleanupMapper` 增 `deleteAiKnowledgeByApp`（按 `app_name`，含 `app_name=''` 的全局结论需显式声明是否一并删，默认保留）。
- `chat_message` 表**无 `app_name` 列**（仅 `session_id`），无法按应用直接清理：先补 `chat_message.app_name` 列（AI 会话创建时写入当前应用），再增 `deleteChatMessagesByApp`；未部署前该表不纳入清理，避免误删跨应用会话。
- `DataCleanupService.cleanupByAppName` 纳入两表，返回计数。
- 单测：清理覆盖表清单断言 + `ai_knowledge` 确实被删；`chat_message` 在补列前不参与清理。

### 批次 2（P1）：可观测性与防呆

#### P1-1 Actuator + 启动自检

- 引 `spring-boot-starter-actuator`，暴露 `health,info,metrics`；`management.endpoints.web.exposure.include` 白名单控制，`health` 需绕过 JWT 白名单或在 `AuthFilter` 放行 `/actuator/health`。
- 自定义 `HealthIndicator`：DB 连通（`DataSource` 校验查询）、源码存储目录可写、剩余磁盘空间（低于阈值 `DOWN` 或 `OUT_OF_SERVICE`）、AI 连通性（可选，无 key 时 `UNKNOWN`）。
- 启动自检 `ApplicationRunner`：检查表结构版本、必需表存在、分区工具可用（MySQL 版本 >= 5.7 且分区表引擎正确），不通过时打印可操作指引（不阻止启动，可配置严格模式）。

#### P1-2 列表统一游标分页

- 统一游标语义：`cursor`（上一页最后一条的排序键）+ `size`（默认 50，上限 500）+ `hasMore`；返回体 `{items, nextCursor, hasMore}`。
- 时序表用 `(time, id)` 复合游标（`WHERE time < ? OR (time = ? AND id < ?)`），避免深分页 `OFFSET`。
- 涉及：`/api/traces`、`/slow-sqls`、`/slow-commands`、`/jvm/metrics`，其余列表（`/source/repos`、`/api/apps` 等）同样收口到一个 `PageRequest`/`PageResult` 工具类。
- 兼容策略：不传 `cursor` 时行为等价现在的 `limit`（首屏），前端分页组件按 `hasMore` 加载。
- 单测：游标编解码、越界、空结果、排序键相同的时间并列场景。

#### P1-3 repoId 默认值修正

- `AnalyzeCodeIssuesTool`：`repoId` 从参数表标为必填；缺失/非法时不落库，返回"可用仓库清单（id + repoName）"让模型向用户确认，并明确提示"将创建问题记录"。
- 若 `source` 参数缺失同样返回可选来源清单。
- 单测：缺 `repoId` 时不调用 service 且返回清单；非法 `repoId`（不存在）拒绝。

### 批次 3（P2）：生命周期与闭环

#### P2-1 删除项目接口

- `DELETE /api/source/repos/{repoId}`：删除 `source_repo` + `source_file` + 磁盘源码目录（`storage-dir/<repoName>`，需防路径穿越：解析后校验仍在根目录内）。
- 关联数据：调用 `DataCleanupService`（按 app_name）；若仓库仅绑定单 app 则一并清理，多 app 绑定需返回确认信息。
- 二次确认：请求体带 `repoName` 精确匹配，避免误删；删除前校验无进行中压测任务。
- 审计日志 + `ProjectRegistry.evict()`。

#### P2-2 apply-fix 修复回写

- `POST /api/source/issues/{issueId}/apply-fix`：入参支持分支名 / PR 链接 / 补丁内容（三选一）。
- 流程：记录修复来源 → 关联 `fix_suggestion` 状态置为"已应用" → 自动创建/触发验证（复用 `IssueVerifyService`，绑定重放压测）→ 回写验证结果。
- 新增 `fix_apply_record` 表或用 `fix_suggestion` 扩展列（`applied_at` / `applied_ref` / `verify_task_id`），保持幂等（同一 issue 重复 apply 返回已有记录）。
- 前端：修复方案页加"回写修复"入口与状态展示。

#### P2-3 压测模板沉淀

- 新增 `stress_template` 表（name / app_name / 请求配置 JSON / 并发 / 时长 / warmup / rampUp / stages / 创建人 / 时间）。
- 接口：`GET/POST /api/stress/templates`、`DELETE /api/stress/templates/{id}`。
- 前端：压测表单加"保存为模板"与"从模板填充"。

### 批次 4（P3）：按需

- i18n：先把后端文案与前端模板中文抽到资源文件（`messages.properties` + `vue-i18n`），默认 zh-CN，预留 en-US。
- 无障碍：统一按钮 `aria-label`、表格 `role`、键盘可达（Tab/Enter/Esc）、焦点可见。
- 明暗主题：CSS 变量化现有深色，加切换开关并持久化到 localStorage。

## 三、执行顺序与验收

1. 批次 1 三项（P0）→ 优先合入，全部补单测 + MySQL 端到端脚本验证（分区新增/删除真实生效、trace 批量写行数一致、清理后 `ai_knowledge` 为空）。
2. 批次 2（P1）→ Actuator/自检、分页、repoId 修正。
3. 批次 3（P2）→ 删除项目、apply-fix、压测模板。
4. 批次 4（P3）→ 按实际需要排期。

每批验收统一：`mvn -B test`（server/datagen/agent）+ 前端 `npm ci && build`，P0 额外跑一次真实 MySQL 端到端脚本；改动点同步更新 `docs/design/*` 与相关 README 说明。

## 四、风险与取舍

- 分区 DROP 不可逆：只删超出保留期的整分区，且保留期可配为 0 关闭；首次上线建议先只建分区、观察一轮再开 DROP。
- 分页改造会动前端调用处：保留 `limit` 首屏语义做兼容，前端分批迁移，避免一次性大改。
- Actuator 暴露面：仅内网 + 白名单路径，`metrics` 不暴露敏感标签。
- apply-fix 涉及代码回写权限：仅管理员账号，且记录可审计。
