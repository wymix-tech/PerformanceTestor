# 运维与数据生命周期加固方案

> 依据：ISSUE #14 评估报告（289 Java 文件 / 25 Vue 组件 / 21 张表全量回查）。
> 原则：只动有实据的问题，每个改动点配套单测/验收，不引入不必要依赖。

## 一、问题清单与影响

## 二、分批修改方案

### 批次 1（P0）：数据可靠性与写吞吐

#### P0-1 分区自动维护 + 保留策略

新增 `PartitionMaintainer`（`@Scheduled`，建议 1h 一次 + 启动时执行一次）：

1. 读取 `perf.retention` 配置：`jvm-metric-days` / `stress-sample-days` / `trace-chain-days` / `slow-sql-days`，`0` 表示不清理。
2. 对 `jvm_metric`（`collect_time`）、`stress_sample`（`sample_time`）：查询 `information_schema.PARTITIONS` 现有分区，为 T+1 / T+2 补齐 `pYYYYMMDD` 分区，并在 `p_max` 存在时用 `REORGANIZE` 保证 MAXVALUE 仍在最后。
3. 按保留期 DROP 早于阈值的分区（分区名日期解析，避免按行 DELETE 造成大事务）。
4. `trace_chain` / `slow_sql` 保留期用分批 DELETE（如每批 5000 条 + 循环），并走 `LIMIT` 保护。
5. 全部 SQL 加超时与 try/catch，失败只告警不影响主流程；执行结果落日志（新建/删除分区名与行数）。

配套：
- `application.yml` 增 `perf.retention.*`。
- 建表脚本补充分区说明与初始分区；保留期写进 `docs/design/database-design.md`。
- 单测：分区名计算（含跨月/跨年）、保留期边界（恰好在阈值当天不删）。

#### P0-2 trace 批量写

- `TraceChainMapper.xml` 增 `batchInsert`（`<foreach>` + `ON DUPLICATE KEY UPDATE`，语义与现 `insert` 一致）。
- `saveTraces` 改为先收集 list 再 `insertInChunks(batch, traceChainMapper::batchInsert)`，复用现有 `INSERT_CHUNK=200` 防 `max_allowed_packet`（`trace_json` 为重列，建议 trace 专属 chunk 更小，如 100，可配置）。
- 收敛：`saveJvmMetrics` 也改为走 `insertInChunks`（当前一次性 batch 未分片），保持四个类型统一。
- 单测：批量 SQL 拼接条数、空列表不执行、分片边界（200/201/500）。

#### P0-3 缓存失效与清理一致性

- `ProjectRegistry` 增 `evict(String projectName)` 与 `evictAll()`；`SourceManager` 在导入成功、改名、删除后调用（P2-1 删除接口一并接入）。
- `DataCleanupMapper` 增 `deleteAiKnowledgeByApp`（按 `app_name` 精确匹配，**不涉及** `app_name=''` 的全局结论，决策见 §二·5）。
- `chat_message` 表**无 `app_name` 列**（仅 `session_id`），无法按应用直接清理：先补 `chat_message.app_name` 列（AI 会话创建时写入当前应用），再增 `deleteChatMessagesByApp`；未部署前该表不纳入清理，避免误删跨应用会话。
- `DataCleanupService.cleanupByAppName` 纳入两表，返回计数。
- 单测：清理覆盖表清单断言 + `ai_knowledge` 确实被删；`chat_message` 在补列前不参与清理。

**实施中的两处口径修正**（比原方案更严谨，已在代码注释与本文件同步）：

1. **保留期边界改「早于」而非「小于等于」**：原方案写「分区名日期解析，早于阈值 DROP」，但未明确「保留 30 天」是否含今天。现定义为：保留最近 30 个完整日期 = 今天起往前数 30 天，即最早保留 `today-(keepDays-1)`；只有整分区数据全部过期的分区（`< today-(keepDays-1)`）才 DROP。避免把「仍有部分时刻落在窗口内」的当天分区整块删掉。
2. **`DELETE ... LIMIT` 不能参数化**：MySQL 的 `LIMIT` 绑定由 JDBC `useServerPrepStmts` 决定，行为随驱动/版本漂移（要么被驱动改写成 offset 语义，要么直接报错）。故批大小以整数白名单常量方式拼接（非外部输入），并在 `RetentionSqlScriptTest` 用断言锁死「只有表名/列名/分区名可 `${}`，时间边界与批大小必须 `#{}`」。

### 二·5 `ai_knowledge` 全局结论（`app_name=''`）的处理决策

> 本节针对 ISSUE #14 中"`ai_knowledge` 全局结论按应用清理时怎么处理"的待确认项给出结论与实现细节。

**现状事实（已回查源码）**：

- `ai_knowledge.app_name` 为 `NOT NULL DEFAULT ''`，空串即"全局结论"；演示数据 `id=2`（预热与阶梯加压的必要性）就是全局条目。
- 检索语义二义：`AiKnowledgeMapper.xml` 的 `search` 与 `recent` 在传入 `app` 时条件是 `app_name = #{appName} OR app_name = ''`，即**按应用查询也始终混入全局结论**；传入空 `app` 则完全不过滤。
- 沉淀来源双轨：`AiKnowledgeService#save`（AI 会话自动沉淀，`source='ai'`）+ 人工 `INSERT`（`source='manual'`）。
- 现有清理入口是 `POST /api/source/repos/{repoId}/cleanup-data`（`SourceController#cleanupData` → `DataCleanupService#cleanupByAppName`），**复用该入口扩展**，不新增清理解除路径；知识库侧目前只有 `DELETE /api/ai/knowledge/{id}` 单条删除。

**决策：全局结论默认保留，按应用清理只删该应用条目，并提供显式开关**

理由：

1. 全局结论不隶属于任何项目（`app_name=''` 即"跨项目共性经验"，如预热/阶梯加压的通用判读），被单项目"清理历史数据"带走属于语义错误——用户清理的是"项目数据"，不是"平台知识"。
2. 全局结论在检索中本就对**所有**应用可见（`OR app_name=''`），若被某次清理顺带删除，会静默降低其他项目的分析质量，且无痕迹。
3. 语义安全的方向应是"宁可少删、必须显式"：默认保留，需要时用参数显式声明。

**实现细节**：

- `DataCleanupMapper` 增 `deleteAiKnowledgeByApp(String appName)`：条件固定为 `app_name = #{appName}`，**不含** `app_name = ''`，`appName` 为空时返回 0（防御：不允许空 app 触发无过滤删除）；开启开关时另调 `deleteGlobalAiKnowledge()`（`WHERE app_name = ''`）。
- 在既有 `POST /api/source/repos/{repoId}/cleanup-data` 上加可选参数 `includeGlobalKnowledge`（query/body，默认 `false`）：
  - `false`：只删 `app_name = #{appName}`；
  - `true`：额外删 `app_name = ''` 的全局结论，**且要求二次确认**（与 P2-1 删除项目同款：请求体带 `appName` 回显校验）。
- 返回计数区分两个键，避免前端把"全局结论也被删了"显示成同一数字：
  - `aiKnowledge`：本应用条目删除数；
  - `aiKnowledgeGlobal`：全局条目删除数（未开启时恒为 0）。
- 日志：开启全局删除时打 `warn` 级审计日志（操作人、appName、删除条数），便于追溯。
- 检索侧**不改**现有 `OR app_name = ''` 语义（保持"全局经验对所有项目可见"），仅在 `SearchKnowledgeTool` 返回项里保留 `appName` 字段，让模型能区分"本应用结论"与"全局结论"。这一点现已是现状（工具已回传 `appName`），无需改动，但需在提示词里补一句区分说明。

**评审时被指出的两个语义冲突（本次一并裁决）**：

| 冲突 | 裁决 |
|---|---|
| `search` 无命中回落 `recent(...)`，把不相关结论当"参考经验"回填，与提示词"工具返回空 = 暂无数据"矛盾 | **按 P1-2 修**：无命中即返回空列表，去掉 `recent` 回落，提示词补"知识库无命中不代表无问题"。此改动影响检索语义，放在批次 2（P1）执行，与本决策一并落地 |
| 人工 `source='manual'`（含 `id=1,2` 演示数据）与 `source='ai'` 是否区别对待 | **清理时不按 `source` 区分**：`manual` 只是录入方式，不代表豁免。但**演示数据提示**：`init.sql` 的 2 条演示条目（`id=1` 属 `perf-demo`、`id=2` 为全局）在生产部署时应通过 `init_empty.sql` 初始化，避免清理 `perf-demo` 时删掉预期作为样例的条目 |

**验收**：

- 单测：`cleanupByAppName` 后断言 `app_name=''` 的全局条目**仍存在**；`includeGlobalKnowledge=true` 时被删除；`appName` 为空时 `deleteAiKnowledgeByApp` 返回 0 且不执行删除。
- 端到端：造 2 条同应用结论 + 1 条全局结论 → 默认清理 → 全局条目仍在且 `search` 对**其他**应用仍能检索到；开启开关清理 → 全局条目消失，返回计数 `aiKnowledgeGlobal=1`。

**实施中的三处口径决定**：

1. **`hasMore` 用「多取一条」判定**（底层取 `size+1`，返回时丢掉多余那条）：否则"正好取满"与"还有下一页"无法区分，前端只能在空页时才停手，多发一次必空请求。
2. **游标取「实际返回的最后一条」而非多取的那条**：取错会永久跳过一条记录（`MetricQueryServicePagingTest` 已锁死）。
3. **`slow_sql` / `slow_command` 的分页排序键用执行时间，不用耗时**：耗时可被后到的慢 SQL 反超，用它当游标键会漏读/重读；页面上的"耗时排名"由前端合并后排序保留。

- `hotspot_method`、`/api/source/issues`、`/api/apps` 等其余列表**未纳入本批分页**：前者无写入时序且由 agent 周期聚合，后两者有条数上限（50/100），深翻收益低。方案原文写"其余列表同样收口到一个 `PageRequest`/`PageResult` 工具类"，实际按"只改确有翻页需求的四张时序表"收窄——为不存在的第二使用方加抽象层不划算。

**实施中的四处口径决定**（比原方案更收窄，已在代码注释与本文件同步）：

1. **删除项目的数据库三步不加 `@Transactional`**：`ProjectLifecycleService.doDelete` 是同类内部调用，Spring AOP 不会拦截自调用——标注了也不生效，反而给出"有事务保护"的错觉。改为：`DataCleanupService` 自身带事务、索引/记录删除各自单语句原子，**磁盘目录删除刻意放在数据库之后**，避免"事务回滚但目录已删"的不一致。
2. **删除项目会连带清理历史数据，但全局 AI 结论始终保留**：删项目复用 `cleanupByAppName(appName, false)`，即不开启 `includeGlobalKnowledge`——删项目是"清掉这个项目的一切"，而全局结论属于平台知识不隶属于任何项目，语义与 §二·5 一致。需要连全局一起清时仍走既有 `cleanup-by-app` 入口显式开启。
3. **apply-fix 的幂等键是「问题 + 来源类型 + 来源标识」**：三者全同才走幂等分支。只按 issueId 幂等会让"又改了一版（换 PR）"被吞掉；只按 source 幂等则无法区分同一分支的多次提交。换来源 = 视为新一版修复，更新记录并重新触发验证。
4. **验证触发异常不阻断回写落库**：验证线程池满/引擎异常时，`applied_at`/`apply_ref` 照常写入——"改了什么"是基础事实，"验证成功与否"是后续结论，前者丢失比后者更严重。此时 `verify_task_id=0` 并在 message 里说明原因。

**实施中的五处口径决定**（已同步进代码注释与本文件）：

1. **主题变量用「R G B 三段裸数值」而非 hex**：Tailwind 的 `<alpha-value>` 才能注入透明度，`bg-bg-card/70` 这类既有透明度修饰符无需改写即可继续工作；若写 hex，全站透明度类会静默失效。
2. **覆盖 Tailwind 内置 `white` 指向 `--overlay`**：组件里 138 处 `bg-white/5` / `border-white/10` 表达的是"在底色上提亮一层"，浅色下白叠白不可见。改为语义变量后，深色=白、浅色=黑，**零组件改动**实现双主题可用——比逐个改写 138 处风险低得多。
3. **后端 i18n 只迁移鉴权与全局异常，不做全量替换**：全仓库有 137 处中文 `ApiResponse.message`，一次性替换会引入大量错译与回归风险，且非本批核心。改为"先立基建 + 迁高频入口 + 用 key 对齐/参数占位符一致性测试锁住增量"，其余模块按方案原文"按需迁移"分批进行。
4. **前端 i18n 只抽骨架文案，不追求覆盖率**：登录/导航/404/通用/主题/语言/无障碍等"全站共用 + 用户首选路径"抽取，业务页文案按需迁移。同时用"中英 key 集合完全一致 + 占位符两侧一致 + 无空文案"三条断言防止漏翻。
5. **`--on-neon` 浅色下仍取深色**：浅色主题把霓虹色压暗为 `#00A876` 后，白字对比度仅约 3.0（不达 WCAG AA 4.5），深色 (`#0B1220`) 在同色上约 4.7。故按钮/强调块上的文字与底色解耦，明暗两套都取深色。

1. 批次 1 三项（P0）→ 优先合入，全部补单测 + MySQL 端到端脚本验证（分区新增/删除真实生效、trace 批量写行数一致、清理后本应用 `ai_knowledge` 为空且全局结论留存）。

## 四、风险与取舍
- `ai_knowledge` 全局结论（`app_name=''`）**默认不被按应用清理删除**，需 `includeGlobalKnowledge=true` 显式开启；检索语义保持"全局经验对所有应用可见"不变。

- 分区 DROP 不可逆：只删超出保留期的整分区，且保留期可配为 0 关闭；首次上线建议先只建分区、观察一轮再开 DROP。
- 分页改造会动前端调用处：保留 `limit` 首屏语义做兼容，前端分批迁移，避免一次性大改。
  **已落地口径**：`limit` 仅在未传 `size` 时生效；前端 4 个视图已迁移到 `{items,nextCursor,hasMore}`，
  `api/index.ts` 的 `normalizePage` 对旧裸数组响应做兜底，避免灰度期两端不同步直接崩。
- 游标分页的排序键必须翻页期间稳定：故慢 SQL/慢命令用**执行时间**而非页面热点的**耗时**，
  耗时会被后到的慢 SQL 反超，用它当游标键必然漏读/重读。
- Actuator 暴露面：仅内网 + 白名单路径（`health,info,metrics`），`env`/`heapdump` 等不暴露，
  `metrics` 不暴露敏感标签。
- 启动自检默认**不阻断启动**（`fail-fast=false`）：容器编排下平台常先于 MySQL 启动，
  fail-fast 会把"库还没起来"变成"平台起不来"的循环依赖；需要严格把关时显式开启。
- apply-fix 涉及代码回写权限：仅管理员账号，且记录可审计。
